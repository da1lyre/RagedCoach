# DESIGN.md

Документ описывает проект Raged Run.

---

## 1. Бизнес-задача

Бегуны-любители ведут заметки о тренировках в разных приложениях. Проблема в том, что эти заметки не связаны между собой и из них трудно делать выводы, оценивать результаты. Непонятно - почему в одни дни результаты растут, а в другие падают.

Raged Run решает эту задачу: собирает субъективные записи и объективные метрики в одном месте, находит скрытые закономерности и отвечает на вопросы спортсмена на естественном языке.

### Целевая аудитория

- Бегуны-любители, тренирующиеся пару раз в неделю
- Тренеры, работающие с несколькими спортсменами

### Ключевая ценность

- Понимание, что именно влияет на результат: сон, углеводы, стресс, объём
- Персональные рекомендации по режиму и питанию
- Раннее предупреждение о перетренированности
- История тренировок в одном структурированном месте

### Сценарии использования

1. Пользователь записывает пробежку вручную или импортирует с трекера.
2. Пользователь задаёт вопрос: "Почему пульс был высоким 15 июня?"
3. Система находит похожие дни, выявляет причины, отвечает со ссылками на источники.
4. Пользователь видит недельный дашборд с трендами по темпу, пульсу, сну.
5. Система автоматически публикует инсайты: "4 пробежки в неделю дают лучший прогресс".

## 2. Метрики

Приложение разворачивается локально на машине пользователя. Все компоненты работают в Docker. Данные не покидают устройство.

### Производительность

- Latency API: P50 до 100 мс, P95 до 300 мс.
- Latency эмбеддинга: P50 до 80 мс, P95 до 200 мс.
- Latency векторного поиска в Qdrant: P50 до 30 мс.
- Latency инференса LLM: P50 до 5 сек, P95 до 12 сек для Qwen3-0.6B на CPU.
- Time to first token: P50 до 500 мс.
- Открытие приложения: до 1.5 сек.
- Открытие списка записей: до 300 мс.
- Запись в Postgres: P95 до 30 мс.
- Пересчёт инсайтов: до 1 сек на 1000 записей.

### Ресурсы

- Память Ollama: до 1.5 ГБ.
- Память Postgres: до 200 МБ.
- Память Qdrant: до 300 МБ.
- Память FastAPI: до 150 МБ.
- Размер LLM: до 500 МБ (Qwen3-0.6B в Q4).
- Размер модели эмбеддингов: до 120 МБ.
- Размер индекса Qdrant: до 200 МБ на 100 тысяч векторов.
- Размер базы Postgres: до 100 МБ на пользователя.

### Качество RAG

- Recall@5: не ниже 0.85.
- MRR: не ниже 0.70.
- Faithfulness: не ниже 0.85.
- Answer Relevance: не ниже 3.5 из 5.
- Hallucination Rate: не выше 12 процентов.
- Доля ответов с корректными источниками: не ниже 0.9.
- Доля корректных отказов при нехватке данных: не ниже 0.95.

### Качество инсайтов

- Доля инсайтов, отмеченных как полезные: не ниже 60 процентов.
- Ложные срабатывания детекции аномалий: не выше 15 процентов.
- Минимум записей для первого инсайта: 10.
- ROC-AUC модели перетренированности: не ниже 0.85.

### Стабильность

- Сессии без ошибок JavaScript: не ниже 99 процентов.
- Успешные записи в Postgres: не ниже 99.9 процентов.
- Восстановление после перезапуска контейнеров: 100 процентов.
- Падения при работе с LLM: не выше 1 процента.
- Fallback на шаблонный ответ: не более 1 секунды.

## 3. Продуктовая задача

Приложение состоит из шести разделов:

1. Дневник бега. Форма записи пробежки и список прошлых записей с фильтрами.
2. Статистика. Сводные метрики: количество пробежек, дистанция, время, средний темп.
3. Инсайты. Автоматически найденные закономерности с уровнем уверенности.
4. AI-тренер. Чат с RAG-системой по данным пользователя.
5. Питание. Рекомендации по питанию до и после пробежки.
6. Сон. Метрики восстановления и график за неделю.

Каждая запись содержит:

- тип пробежки (легкая, темповая, интервалы, длинная, восстановительная)
- дату
- длительность в минутах
- дистанцию в километрах
- средний пульс
- калории
- текстовую заметку
- самочувствие (отлично, хорошо, средне, тяжело, болен)

## 4. Ограничения среды

### 4.1 Платформа

Проект работает только на десктопе. Windows, macOS, Linux. Мобильные устройства не поддерживаются.

Причины:

- Docker не работает на iOS и Android без root.
- Qwen3-0.6B требует больше памяти, чем доступно на телефоне.
- Инференс на мобильных батареях разряжает устройство за час.
- Форма ввода и таблицы неудобны на маленьком экране.

### 4.2 Работа без интернета

После первого запуска приложение работает полностью офлайн. Все компоненты локальные, внешние API не используются.

Требования:

- Все данные хранятся в Postgres внутри Docker volume.
- Векторный поиск работает через Qdrant внутри Docker.
- AI-тренер работает через Ollama внутри Docker.
- Внешние сетевые запросы не выполняются, кроме первичной загрузки образов и модели.

### 4.3 Локальные инструменты

- Хранение записей. PostgreSQL 15 в Docker, порт 5432.
- Векторный поиск. Qdrant в Docker, порт 6333.
- Эмбеддинги. Sentence-transformers, модель multilingual-e5-small, на CPU.
- LLM. Ollama в Docker, порт 11434. Модель Qwen3-0.6B в Q4.
- OCR. Tesseract в контейнере бэкенда.
- Парсинг FIT. Python-библиотека fitparse.
- API. FastAPI в Docker, порт 8000.
- Фронтенд. Nginx со статикой, порт 8080.

### 4.4 Docker как единственная зависимость

Пользователь не ставит Postgres, Qdrant, Ollama и Python вручную. Всё делает Docker Compose.

Один `docker-compose up` поднимает пять контейнеров:

- postgres. База данных.
- qdrant. Векторная база.
- ollama. LLM-сервер с Qwen3-0.6B.
- api. FastAPI-бэкенд.
- web. Nginx со статикой фронтенда.

Через две минуты приложение доступно на `localhost:8080`. Модель пуллится автоматически.

### 4.5 Требования к системе

- ОС: Windows 10 и выше, macOS 12 и выше, Ubuntu 20.04 и выше.
- Процессор: 4 ядра, x86_64 или arm64.
- RAM: минимум 6 ГБ, рекомендуется 12 ГБ.
- Диск: 5 ГБ свободного места.
- Docker Desktop или Docker Engine.
- Браузер: Chrome, Firefox, Safari или Edge последних версий.

### 4.6 Экспорт и бэкап

- Кнопка "Экспорт" отдаёт JSON со всеми записями пользователя.
- Бэкап Postgres через `pg_dump`.
- Бэкап Qdrant через снапшоты коллекции.
- Автоматическая синхронизация между устройствами не поддерживается.

### 4.7 Приватность

- Данные не покидают машину пользователя.
- Нет аккаунтов, нет внешней аутентификации.
- Нет телеметрии и аналитики.
- Внешние запросы не выполняются, кроме первичной загрузки Docker-образов и модели.

## 5. ML-задача

Проект решает три ML-задачи.

### 5.1 Retrieval-Augmented Generation

Задача: на вход приходит вопрос пользователя на естественном языке. Нужно найти релевантные фрагменты истории тренировок, восстановления и питания, и сгенерировать ответ, опирающийся только на эти фрагменты.

Пайплайн:

1. Ingestion. Каждая запись пользователя превращается в структурированный документ: текст заметки, метаданные (дата, тип, дистанция, пульс, самочувствие), агрегаты дня (сон, углеводы, стресс).
2. Chunking. Документы разбиваются на чанки размером 256-512 токенов с перекрытием 20 процентов. Для коротких заметок чанк равен документу.
3. Embedding. Чанки превращаются в векторы моделью multilingual-e5-small через sentence-transformers на CPU бэкенда.
4. Indexing. Векторы складываются в Qdrant с payload: user_id, date, workout_type, distance_km, avg_hr, mood.
5. Retrieval. На запрос пользователя выполняется hybrid search: dense (векторный) плюс sparse (BM25) с последующим переранжированием.
6. Generation. Топ-K чанков попадают в промпт Qwen3-0.6B. Модель работает в Ollama-контейнере. Формирует ответ со ссылками на источники.
7. Post-processing. Ответ фильтруется на галлюцинации через проверку цитируемости: каждое утверждение должно быть подтверждено чанком.

### 5.2 Поиск закономерностей

Задача: находить статистически значимые связи между факторами и результатами, чтобы формировать инсайты без участия человека.

Методы:

- Корреляционный анализ (Spearman) между парами: углеводы и темп, сон и пульс, стресс и восстановление.
- Анализ временных лагов: влияние сна предыдущей ночи на темп сегодня.
- Сегментация недель: кластеризация недель по объёму и интенсивности, поиск лучших режимов.
- Детекция аномалий: пульс в покое выше baseline на 7 ударов, темп хуже обычного на 10 процентов.

Все вычисления выполняются на бэкенде в Python через pandas и scipy.

Каждая закономерность имеет:

- уровень уверенности (0-100 процентов), рассчитывается на основе объёма выборки, величины эффекта и статистической значимости
- минимальное количество наблюдений (по умолчанию 10)
- период, за который она найдена

### 5.3 Предсказание перетренированности

Задача: бинарная классификация состояния спортсмена по недельному окну.

Признаки:

- средний пульс в покое
- вариабельность сердечного ритма (HRV)
- средняя продолжительность сна
- тренировочный объём
- соотношение острая и хроническая нагрузка (ACWR)

Модель: gradient boosting (XGBoost или LightGBM) на бэкенде. Метрика: ROC-AUC на отложенной выборке, целевое значение не ниже 0.85.

## 6. Метрики оценки RAG

Качество RAG-системы измеряется на трёх уровнях: retrieval, generation и end-to-end.

### 6.1 Retrieval

- Recall@K. Доля запросов, для которых правильный документ попал в топ-K. Целевое значение Recall@5 не ниже 0.85.
- Precision@K. Доля релевантных документов в топ-K.
- MRR (Mean Reciprocal Rank). Средний обратный ранг первого релевантного документа.
- NDCG@K. Нормированный дисконтированный накопленный выигрыш с учётом позиции.
- Hit Rate. Доля запросов, где хотя бы один релевантный документ найден.

### 6.2 Generation

- Faithfulness. Доля утверждений в ответе, подтверждённых retrieved-контекстом. Целевое значение не ниже 0.85.
- Answer Relevance. Соответствие ответа вопросу, оценивается LLM-судьёй по шкале 1-5. Целевое значение не ниже 3.5.
- Context Precision. Доля релевантного контекста в промпте.
- Context Recall. Покрытие эталонного ответа retrieved-контекстом.
- Hallucination Rate. Доля ответов, содержащих неподтверждённые утверждения. Целевое значение ниже 12 процентов.

### 6.3 End-to-End

- Человеческая оценка ответов по 5-балльной шкале. Разметка 200 вопросов, 3 аннотатора, метрика согласия Cohen's kappa не ниже 0.7.
- Доля ответов с корректными ссылками на источники. Целевое значение не ниже 0.9.
- Время ответа. P50 не выше 5 секунд, P95 не выше 12 секунд для Qwen3-0.6B.

### 6.4 Эталонный датасет

Собирается вручную: 300 вопросов пользователей, для каждого известен правильный ответ и правильные источники. Разбивается на три части: factoid (60 процентов), аналитические (30 процентов), многошаговые (10 процентов).

## 7. Архитектура

### 7.1 Компоненты

Фронтенд. Одностраничное приложение на HTML, CSS и JavaScript. Обращается к API по REST. Никаких данных локально не хранит, кроме кэша статики.

API. FastAPI. Отвечает за аутентификацию по имени, CRUD тренировок, инсайты, чат с RAG, метрики.

Postgres. Хранит пользователей, тренировки, метаданные, логи чатов, инсайты.

Qdrant. Хранит эмбеддинги чанков с payload: user_id, date, workout_type, distance_km, avg_hr, mood.

Ingestion. Модуль бэкенда, превращающий записи в чанки и обновляющий Qdrant при каждом изменении тренировки.

RAG-оркестратор. Модуль бэкенда, объединяет retrieval, reranking и generation.

Ollama. Контейнер с Qwen3-0.6B. Принимает HTTP-запросы от API на `ollama:11434`.

### 7.2 Поток данных

1. Пользователь открывает приложение. Nginx отдаёт статику.
2. Пользователь сохраняет пробежку. Фронтенд шлёт POST на API.
3. API пишет запись в Postgres.
4. Ingestion получает событие и обновляет Qdrant: удаляет старые чанки, создаёт новые, пересчитывает эмбеддинги.
5. Пользователь открывает AI-тренера и задаёт вопрос.
6. API передаёт запрос в RAG-оркестратор.
7. Оркестратор делает retrieval из Qdrant, rerank, формирует промпт.
8. Промпт уходит в Ollama.
9. Qwen3-0.6B генерирует ответ. Он возвращается с массивом источников.
10. Лог запроса и ответа сохраняется в Postgres для офлайн-оценки.

### 7.4 Безопасность

- Аутентификация по имени с выдачей user_id.
- На каждый запрос проверяется принадлежность тренировки пользователю.
- Векторный поиск в Qdrant всегда фильтруется по user_id.
- Ollama доступен только внутри Docker-сети.
- Postgres и Qdrant доступны только на localhost.
